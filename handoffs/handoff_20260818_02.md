## Decisions & conventions
- **File-based save/load uses two plain functions, not the full `ProgressStorageAdapter`
  interface** §2 sketches — reshape into that interface only once Phase 2 (`localStorage`)
  actually needs the polymorphism (YAGNI with only one adapter implemented so far).
- **Dashboard thumbnails hide the solution path — confirmed explicitly with the user**
  (asked via AskUserQuestion before building) — achieved for free by passing `null` as
  `solutionTrace` into the pre-existing `hydrateDraftFromMazeData`, which skips path
  application entirely when no trace is given. Do not pass the real trace here without
  asking first — this was a deliberate anti-spoiler choice for the level-designer overview.
- **`CellRenderer` is purely presentational, per its pre-existing fixed type** — no click
  handlers, no neighbor lookups. All interactivity (click-to-place, drag-to-draw,
  wall-toggle buttons, invalid-cell highlighting) stays owned by `PickaxeGrid`, layered on
  top as separate absolutely-positioned elements sharing the same geometry constants.
- **Any future absolutely-positioned element whose box intentionally straddles two grid
  cells (like the wall rectangles) needs an explicit `z-index`** — without one, whichever
  cell is later in DOM order silently wins paint/hit-testing on the overlapping region.
  This bit the wall-toggle buttons this session; watch for it if any future overlay
  (e.g. a hypothetical corner decoration) does the same edge-straddling trick.
- `[[feedback_spec_conflicts]]` (existing memory) continues to apply — no
  `development_plan.md` numeric constants were touched; both sessions' plans were
  presented via plan mode and approved before implementation, with one explicit
  AskUserQuestion for the thumbnail-path ambiguity the doc didn't resolve.
