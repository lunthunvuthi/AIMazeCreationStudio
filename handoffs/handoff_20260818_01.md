   canned shape every time (read as "static") plus a jarring swap (read as "wrong/different
   seed"). Rebuilt per explicit user decision (clean progressive reveal, no flicker of
   non-final walls) to: wait for the real `/api/maze/generate` result **first** (a
   "Generating the maze…" spinner, no fake data shown), then animate strictly from that real
   data (real S/G, the real solution path segment-by-segment, every real wall progressively
   appearing — path-walls first, then the rest — nothing ever shown gets corrected later).
   Deleted `registry/pickaxe/randomizeCosmetics.ts` (built for the old design, no longer
   needed). Added reusable helpers to `wizardMaze.ts`: `hydrateDraftFromMazeData`,
   `clearWalls`, `setCellKind`, `listWallEdges`.
   - **Known trade-off, not yet re-discussed with the user**: total wait is now fetch-time +
     animation-time *stacked* (previously overlapped to hide the fetch), so a slow star-8
     fresh randomize could take up to ~15-19s total instead of the old ~7-11s. The user
     asked for correctness over the speed illusion, so this was accepted as the necessary
     consequence, but worth surfacing if it feels too slow once used more.
4. **Redesign #2 — StrictMode cancellation bug**, found while verifying #3 live (Playwright
   snapshot comparison showed the popup's last frame genuinely didn't match the final
   result — a real bug, not a test artifact). Root cause: the modal's async animation loop
   used a single `useRef` cancellation flag reset at the top of every effect run; React
   `StrictMode` (on in `main.tsx`) double-invokes effects in dev, so the first (stale)
   invocation's in-flight `run()` (a fresh `generateMaze` call, i.e. a genuinely different
   random seed) could still resolve and write state *after* the second invocation had already
   reset the shared flag to `false` — two different backend results got interleaved into the
   same render. Fixed to the standard React pattern: a `let cancelled = false` scoped
   **locally to each effect invocation**, not a shared ref. This isn't StrictMode-only — the
   same shared-ref pattern would have misfired on a fast double-click of a reroll button too.

## Decisions & conventions
- **Animation must use ONLY real backend data, never a placeholder** — confirmed emphatically
  by the user this session after the cosmetic-preview design confused them. Do not
  reintroduce any "illustrative/cosmetic while fetching" approach without asking first.
- **Stage 4 (walls) is a clean progressive reveal, no flicker** — user explicitly chose this
  over keeping some chaotic appear/disappear, once told that flicker would have to use real
  (but non-final) wall positions to stay honest. If a "walls appear AND disappear" flair is
  wanted again later, it needs a design that only ever shows the true final wall set at any
  point — e.g. flickering among the maze's actual required-vs-distraction wall candidates
  isn't safe either, since a snapshot mid-flicker could still look "wrong."
- **Async effect cancellation flags must be scoped locally (`let cancelled = false` inside
  the effect), never a shared `useRef`** — StrictMode's dev double-invoke (and any fast
  re-trigger) will interleave stale and fresh async work otherwise. Apply this pattern to any
  future component with a similar "kick off an async op in an effect, cancel on cleanup"
  shape.
- **Reroll demotes `'complete'` back to `'randomized'`**, requiring Complete again —
  consistent with the manual wizard's existing "any edit invalidates" rule.
- `[[feedback_spec_conflicts]]` (existing memory) still applies: didn't touch
  `development_plan.md`'s numeric constants without asking; the design decisions above were
  all confirmed with the user first (one `AskUserQuestion` on the stage-4 flicker question).

## Gotchas / watch-outs
- `PickaxeGrid.tsx`'s cell `onClick`/`cursor-pointer` gating must stay
  `mode === 'place-sg' || mode === 'draw-path'` — narrowing it to just `'place-sg'` (an easy
  mistake when adding the read-only `'view'` mode) silently breaks the manual wizard's Draw
  Path tap-to-extend input method. Caught once this session via a live Playwright
  click-through of the manual wizard, not any automated regression test (none exist).
- **No test runner in this repo** (no vitest/jest/Playwright as a dependency) — verification
  this session was ad hoc Node + Playwright driver scripts written to the scratchpad
  directory and deleted after use, run against the user's already-running `uvicorn`+`vite`
  dev servers (never touched/restarted those processes — same PIDs throughout: uvicorn
  39370, vite 39287 as of this session).
- **StrictMode double-invokes effects in dev** — any future Playwright test that mocks a
  network response with a "single-shot toggle" (fail once, then pass) will misbehave, because
  the mock gets consumed by the throwaway invocation while the surviving one goes through
  unmocked. Mock unconditionally while the route is active, then `unroute` before triggering
  a retry, as this session's final verification script does.
- `VITE_FAST_ANIM=1` env var convention (read via `import.meta.env.VITE_FAST_ANIM` in
  `RandomizeProgressModal.tsx`) shrinks all animation durations to ~5% for fast manual/
  Playwright iteration — real timers still fire, production timing is untouched by default.
