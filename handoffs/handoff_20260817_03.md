## Decisions & conventions
- **`min_walls` is a floor everywhere, not an exact target** — including star 1 (was
  "exactly 1", user approved changing to "at least 4" after seeing exhaustive-search proof
  that 1-3 walls can never produce a unique solution). This is because every wall in this
  game is breakable given enough pickaxes — there's no permanent barrier — so sparse wall
  layouts on open grids very often have many equal-pickaxe-cost alternate routes, not just
  one. The generator's fix: bias the ideal path short (fewer free detour cells) AND
  escalate wall density well past the stated minimum (up to walling every off-path edge)
  across retry attempts, rather than a small fixed increment.
- **Stop and ask before editing a design doc's numeric constants**, even when the doc
  itself calls them adjustable placeholders — confirmed as the right call this session via
  `AskUserQuestion`; saved as a durable feedback memory
  (`~/.claude/projects/.../memory/feedback_spec_conflicts.md`). Once a general principle is
  approved (e.g. "floor not target"), applying it to further instances of the same
  conflict without re-asking is fine — only re-ask when a new instance doesn't clearly fall
  under an already-approved principle.
- **`min_walls`/`max_walls` in `STAR_PARAMS`**: only star 1 ever had `max_walls`, and it was
  removed (see above) — no star currently has a wall-count ceiling.
- Reports from `pickaxe-maze validate` are written to `output/`, not next to the input file
  — reasoned as the more consistent split (input/ = fed in, output/ = tool-produced), but
  this was a judgment call, not something the user explicitly requested; easy to change to
  "same folder as input" if preferred.
- Python packaging choice was explicitly asked and answered: **venv + `pyproject.toml`**
  over uv/Poetry (neither installed on this machine; user picked the zero-extra-tooling
  option).
- Tests use stdlib `unittest` (pytest wasn't installed when validator/generator tests were
  first written) but are pytest-compatible and now run via pytest post-packaging.

## Gotchas / watch-outs

  needs quotes (`"PickAxe Maze Creation/..."`) or escaped spaces. The user hit this
  directly with `pickaxe-maze validate PickAxe Maze Creation/input/foo.json` (unquoted →
  shell splits it into 3 args → argparse error). Not a CLI bug, just needs quoting. Offered
  to rename the folder to remove spaces; user has not yet decided.
- The repo has **no git history** — if the user asks to init git at some point, check
  `.gitignore` is already in place (it is) before the first commit so `.venv/`,
  `__pycache__/`, `*.egg-info/`, `.pytest_cache/` don't get committed.
- `PickAxe Maze Creation/input/` and `output/` currently contain the user's own manual test
  files (`star3_20260817_181122.json` and its report) from verifying the quoting fix live —
  these are the user's, not scratch I created; left in place intentionally.
- The diagnostic message path in `validator.py` (`_diagnose_unsolvable`) has its own
  `_DIAGNOSTIC_STATE_CAP` (300k) separate from the generator's `VALIDATE_MAX_STATES`
  (200k) — they're deliberately independent knobs for different call sites, not a
  duplication to clean up.
- `generate_maze` raises `GenerationError` if it exhausts `MAX_PATH_ATTEMPTS` (50) ×
  `MAX_WALL_ATTEMPTS` (200) without finding a unique solution. Verified this doesn't happen
  in practice across 80 star×seed combinations, but it's theoretically possible for an
  unlucky seed on a not-yet-tested star/seed combination — not currently caught/retried
  anywhere above `generate_maze` itself (fine for CLI use — it just prints an error and
  exits 1 — but the future FastAPI endpoint should decide how to surface this, e.g. retry
  with a fresh seed vs. 500 to the client).
