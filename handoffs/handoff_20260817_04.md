## Decisions & conventions
- **`question_id`/`difficulty_star` naming applies everywhere now** — both CLI commands
  (`generate` and `generate-level`) and the backend/frontend types use these names
  consistently. Do not reintroduce `id`/`star` for this concept.
- Backend response bodies use camelCase only where the frontend spec (§4.2) already
  specifies it (the seed fields) — everything else stays snake_case
  (`pickaxe_count`/`width`/`height`/`maze`), matching `MazeData` verbatim. Don't
  camelCase-ify further without a spec reason.
- Roadmap steps are being built **strictly in order** and un-built steps are left as
  visible "coming soon" placeholders rather than partially implemented — e.g. Modify Maze's
  drag-and-drop and the Save Progress/Export JSON buttons are present in the UI (matching
  the spec's screen layout) but disabled, not silently missing. Keep this pattern for
  future steps: build the shell, stub the not-yet-built behavior visibly, don't leave a
  page missing entirely just because its logic isn't ready.
- CORS on the backend is wide-open (`allow_origins=["*"]`) — an explicit, acknowledged
  Phase-1-only choice (stateless, no auth), not an oversight. Revisit once deployment is
  decided (§1 lists deployment as "not yet decided").
- `[[feedback_spec_conflicts]]` (existing memory): still applies — the `id`/`star`→
  `question_id`/`difficulty_star` rename this session was confirmed via `AskUserQuestion`
  before editing `development_plan.md`'s type definitions, consistent with that memory's
  rule about not silently editing spec docs.
