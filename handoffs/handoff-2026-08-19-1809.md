## Decisions & conventions
- **Renderer tech is hybrid, not backend or frontend-only** — settled, don't
  relitigate. Full rationale in `pdf_export_spec.md` §7 item 5.
- **Page-number placement: odd → top-left, top-right for even** — a direct rule from
  the owner, not derivable from the original sample PDF. Applies to both the plain box
  and the laurel-wreath Bonus variant.
- **Visual sizing multipliers are relative to the pre-this-session baseline**, not
  absolute pixel targets: page-number/laurel badge 2x, pickaxe-count badge 3x, bonus
  mascot 4x. If asked to adjust further, treat these as the new 1x baseline going
  forward unless told otherwise.
- **The bonus page's blank "draw your own maze" spacer is not a locked spec value** —
  it was an implementation estimate (`160mm`, now `84mm`). Shrinking it to make room
  for the bigger mascot was accepted, but if future changes need more/less of that
  blank area, it's fair game to adjust again (just flag the change, per this session's
  pattern — the user's standing preference, per project memory, is to be consulted
  before changing numeric constants in an actual **design doc**; this spacer lives in
  spike code, not a doc, but the same "flag it, don't silently decide" instinct applies).
- **CLI-level proof was deliberately chosen over building the full one-click Download
  pipeline** in this session (via `AskUserQuestion`) — wiring real data in only needed
  to prove the renderer *can* consume it, not stand up a backend service yet.
- All sizing changes scale rendered width/height only (Tailwind classes or explicit
  px), never the SVG `viewBox`/internal coordinate math — keeps proportions correct
  and keeps diffs small/reviewable.

## Gotchas / watch-outs
- **Scaling a fixed-size element can overflow the page.** The 4x mascot change did
  exactly this (5 pages → 6 pages, second page mostly blank) until the blank spacer
  above it was shrunk. Any future "make X bigger" request on this page should be
  re-verified for page count afterward (`pymupdf`: `len(fitz.open(path))`), not just
  visually spot-checked on the page the element is on.
- `Web App/spikes/pdf-renderer/output/*.pdf` are gitignored/untracked — regenerating
  them for testing never shows up in `git status`, so it's safe to overwrite freely
  without worrying about polluting the diff.
- The hybrid render script spawns and kills its own `npm run dev` per run (~several
  seconds of startup) — expect each `node render_via_browser.mjs` invocation to take a
  little while, this is normal, not a hang.
- `render_via_browser.mjs --data` expects a file path to a `LevelProgress`-shaped JSON
  file. There's no sample real save file checked into the repo — the verification this
  session used a hand-modified copy of `Web App/spikes/pdf-renderer/sample_fixture.json`
  (which is itself real-maze-generator output, just with hand-assembled page grouping),
  not an actual dashboard-exported file. If a genuinely dashboard-produced file behaves
  differently, that's untested territory (unverified).
- Two Tailwind sizing styles are mixed in this file on purpose: standard classes
  (`h-24 w-24`) where the target matches Tailwind's scale, arbitrary-value brackets
  (`h-[384px]`, `h-[84mm]`) where it doesn't. Both are already used elsewhere in this
  codebase (e.g. `min-h-[277mm]`), not a new pattern.
